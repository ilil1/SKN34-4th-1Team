# GovBiz Web

운영 평가 상세의 **Prefect 실행 로그**는 관리자 로그인 상태에서 같은 origin의 Ops API로 조회합니다.
최신순 100개씩 페이지를 이동할 수 있고 새로고침으로 새 로그를 확인합니다. 개인 PC의 Prefect 터널 없이
사용하며, 배포 시 `/api/v1/ops/evaluations/{id}/logs`를 제공하는 Ops 이미지도 함께 반영해야 합니다.

지원사업을 AI 대화 또는 직접 선택한 필터로 검색하고 공고의 상세 조건과 원문을 연결하는 웹 화면입니다.
React·TypeScript·Vite·Tailwind CSS를 사용합니다. 전체 기술 구성은
[프로젝트 기술 문서](../../docs/technology.md), 기능별 완료·미구현 범위는
[구현 현황](../../docs/implementation-status.md)을 참고하세요. 계층·DI·MVVM·Redux의 역할은
[아키텍처 README](../../docs/architecture/README.md#frontend-화면과-데이터-처리-분리)에 정리했습니다.

리포트 발송 큐 적용 후에도 기존 상태 enum은 유지합니다. 미발송에는 예약 전·큐 대기를 함께 표시하고,
새 정기 예약을 꺼도 이미 예약된 메일은 처리될 수 있음을 안내합니다. [발송 큐의 설정·상태](../../docs/rabbitmq-daily-report-delivery.md)를 참고하세요.

웹·React Native 앱은 같은 pnpm workspace에서 관리합니다. 공통 domain·DTO 검증·공고 HTTP 클라이언트의
실제 구현은 `frontend/packages/shared`에 있고, 기존 `src/domain`과 `src/data/models`는 호환용 재수출입니다.
새 공통 로직은 `@govbiz/shared/...`를 가져오며 웹 화면·쿠키 인증·Vite 설정은 여기에 둡니다.
전체 실행·공유 경계는 [웹·앱 공동 관리](../../docs/mobile-monorepo.md)를 참고하세요.
요금제의 가격·한도·출시 안내·FAQ는 `@govbiz/shared/design/pricingContent`를 웹과 모바일에서 함께 읽습니다.
웹의 공개·작업 요금제 경로와 버튼 이동은 유지하며 모바일은 같은 내용을 탭 전환형으로 표시합니다.

## 실행

### Vercel 운영 배포 준비

운영 주소는 **[govbiz.vercel.app](https://govbiz.vercel.app)**이며 Vercel 프로젝트 `geonwoo4/govbiz`가
개인 저장소 main의 `frontend/web`에 연결되어 있습니다. 2026-10-11 웹 HTTP 200을 확인했으며,
Core/Ops API는 아직 배포 설정 미완료 503입니다. 외부 API 연결은 아래 EKS 절차를 따릅니다.

Root Directory는 `frontend/web`, Node 24.x/pnpm 11.22.x를 사용합니다. Vercel 프로젝트 설정에서
**Include source files outside of the Root Directory in the Build Step**을 켜서 `frontend/packages/shared`와
루트 workspace/lockfile을 포함합니다. 설치는 저장소 루트에서 웹 의존성만 선택합니다. `vercel.json`은 SPA 라우팅과 API 캐시 금지,
`middleware.ts`는 고정 운영 주소의 `/api`를 CloudFront로 중계하며 프록시 비밀값과 신뢰 사용자 IP를 전달합니다.
미들웨어는 서버 전용이며 UI/AI 실행 코드가 아닙니다. Preview의 운영 API 접근은 차단합니다.
환경값은 [배포 안내](../../docs/deployment-aws-vercel.md)에 정리했습니다. 기존 Vite 개발 프록시는 그대로 유지하며
실제 Vercel 프로젝트 연결·배포는 별도입니다.
프로젝트가 없으면 [Vercel 최초 설정](../../infrastructure/eks/continuous-deployment.md#vercel-최초-설정)을 따릅니다.
개인 저장소 `ilil1/SKN34-4th-1Team` main의 5개 필수 CI 통과 → EKS 배포 성공 → Vercel 빌드·운영 주소 전환 workflow를 준비했습니다.
학교 저장소의 변경은 개인 main에 동기화한 뒤 해당 커밋의 개인 저장소 CI가 통과해야 배포됩니다.
`vercel.json`은 main의 기본 Git 자동 배포를 끄므로, GitHub `eks-production` 설정과
`EKS_RELEASE_ENABLED=true`까지 연결해야 이후 main 병합이 운영 배포로 이어집니다.

현재 AWS 이전 계획도 **웹은 Vercel, 백엔드는 EKS**로 분리합니다.
[EKS 시연 구성](../../infrastructure/eks/sydney-demo.md#웹-배포와-api-연결)의 `--vercel-origin`으로
EKS 웹 Pod를 제외하고 Core·Ops에 실제 웹 주소를 반영합니다. AWS의 외부 HTTPS API 진입점과
Vercel Ops 프록시는 [EKS API 진입점](../../infrastructure/eks/api-entrypoint.md)을 검증한 뒤
Production의 `GOVBIZ_OPS_PROXY_ENABLED=true`로 활성화합니다. 기본값은 503 차단이며,
활성화해도 운영 origin·프록시 비밀값 검사는 유지하고 쿠키·Origin·CSRF 헤더를 전달합니다.

### Docker Compose

저장소 루트의 `.env`와 API 키를 먼저 준비합니다. 상세 설정은
[Compose 실행 안내](../../infrastructure/README.md#실행)에 있습니다.

```bash
docker compose --env-file .env --file infrastructure/compose.yaml up --build
```

브라우저에서 `http://127.0.0.1:5173`에 접속합니다. React는 `/api` 상대 주소로 요청하고,
Vite 개발 서버가 `http://core-service:8080`으로 중계합니다.

### LLMOps 운영 화면 — React + Django

`/ops/*`는 React 운영 화면이며 Django 템플릿을 사용하지 않습니다.

| 화면 | 경로 | 역할 |
| --- | --- | --- |
| 성능 대시보드 | `/ops/dashboard` (`/ops`에서도 연결) | 실측 지표·표본·변화 추이와 평가 상세 진입 |
| 실사용 모니터링 | `/ops/usage` | 서비스의 AI 호출·토큰·비용, 기능·모델·날짜별 집계와 상위 회원, AI 실행 추적 연결 |
| AI 실행 추적 | `/ops/traces`, `/ops/traces/:traceId` | 관리자 인증으로 실행 목록·단계·입출력·오류 조회 |
| 평가 이력 | `/ops/evaluations` | 실행 목록과 답변 검토 진입 |
| 평가 보고서 | `/ops/evaluations/:runId/report` | 평가 자료·모델·질문·한글 지표 해설과 Evidently 원본 차트 |
| 새 평가 | `/ops/evaluations/new` | 자료·평가 모델·비교 대상 선택과 평가 접수 |
| 예산 관리 | `/ops/budget` | 누적·일별 한도와 사용량 관리 |
| 정기 실행 | `/ops/schedules` | 정기 계획과 날짜별 접수 상태 관리 |

선택한 화면의 기능만 표시·조회합니다. 데스크톱은 왼쪽 메뉴, 좁은 화면은 상단 메뉴를 사용합니다.
실사용 모니터링은 기존 `AdminAiCostsPage`와 Core의 `/api/v1/admin/ai-costs` API를 재사용합니다.
호출 흐름은 `LLMOps React → 기존 AI 비용 UseCase·Repository → Core 관리자 API → 사용량 DB`이며,
Ops 평가 DB에 사용량을 복제하지 않습니다. 비용 비교는 Core가 OpenAI Usage·Costs API를 같은 UTC 기간으로 함께 수집한 `comparison`을 사용합니다.
Catalog 색인·평가·직접 호출도 선택한 조직/프로젝트 범위에 포함되며, 회원·기능별 앱 기록은 별도 표로 보여 중복 합산하지 않습니다.
기간과 일별 표는 UTC 날짜(서울 오전 9시 시작), 가져온 시각은 UTC `Z`입니다. 미조회 날짜·미확정 토큰·가격 누락이면 차액을 숨깁니다.
캐시 읽기·쓰기·12시간 쓰기를 구분하며, 확인되지 않은 쓰기 토큰/단가는 0으로 표시하지 않습니다. 진행 중인 날과 지연 집계는 이후 바뀔 수 있습니다.
조회는 모델을 호출하지 않으며, Core가 관리자 세션을 다시 검사하고 기존 조회 감사 기록을 남깁니다.
401은 Ops 세션을 다시 확인해 로그인으로 이동하고, 403·조회 장애는 결과 대신 명시적인 안내를 표시합니다.
호출 수는 기록된 OpenAI 호출 수이며 사용자 요청 수·실패율·응답 시간은 포함하지 않습니다.
AI 실행 추적은 기존 GovBiz 관리자 세션으로 조회합니다. 별도 Langfuse 로그인이나 접속 IP 등록이 필요하지 않습니다.
호출 흐름은 `React → /api/v1/ops/traces → Ops의 Core 관리자 인증 확인 → 서버 내부 Langfuse 조회 API`입니다.
Langfuse 자격 증명은 서버에서만 사용합니다. 기본 최근 7일, 최대 30일, 페이지당 최대 50개를 조회하며
다음 페이지·상세·목록 복귀에도 조회 기간과 필터를 유지합니다. 단계별 입력·출력은 HTML 실행 없이 텍스트로 표시합니다.
401·403은 기존 Ops 세션을 다시 확인하며, Langfuse 장애는 빈 목록으로 숨기지 않고 재조회 안내를 표시합니다.
현재 사용자·비용 기록과 개별 trace의 자동 연결은 없습니다. Catalog 등의 호출은 조직 장부에 포함되지만 회원·기능으로 소급 귀속하지 않습니다.
성능 대시보드는 `GET /api/v1/ops/dashboard`로 최근 요청 200건 안의 실제 모델 평가를 읽습니다.
모델·자료/채점 버전·기간 필터는 URL에 유지되며 새로고침 버튼으로 갱신합니다. 상태 일치율·근거 인용
재현율·검색 재현율·답변 지연과 실측 이력을 제공합니다. 자료·사례·모델·채점 버전·검색 K가 다른
평가는 별도 계열이며 측정 사례까지 같은 경우에만 이전 대비 %p 차이를 표시합니다. 1회만 있으면
추이를 판단할 수 없다고 표시합니다. 미측정 값은 0으로 바꾸지 않습니다.
**모델별 결과 비교**는 선택한 자료·사례·평가 범위·채점 버전·검색 K가 같은 모델들의 기간 내
최신 실측을 나란히 표시합니다. 위의 측정 모델이 차이 기준이며, 프롬프트·모델 외 생성 설정·지표별 측정 사례가
같을 때만 %p 차이를 계산합니다. 다른 조건이나 미측정 값은 차이를 계산하지 않고 이유를 표시합니다.
각 모델의 측정 시각과 평가 상세 링크를 함께 제공합니다. 저장된 결과가 한 모델뿐이면 같은 자료로
다른 모델을 평가하도록 안내하며, 비교 표를 열거나 필터를 바꾸는 것만으로 모델을 호출하지 않습니다.
저장 응답 재평가·합성 검증은 새 실측으로 포함하지 않으며, live 원본의 복구 결과는 원본 시각에
귀속하고 같은 응답을 중복 집계하지 않습니다. Ops의 평가 설정 모델은 실제 서비스의 현재 배포 모델을
검증한 값이 아닙니다. 자동 지표는 사람의 품질 승인과 구분하며, 답변·검토는 상세 평가로 연결합니다.
최근 실측 아래의 **사람 검토와 비교 기준**은 별도 검토 상태 API로 현재 자료의 사례별 검토 수,
참조 승인·답변 전체 승인, 품질 판정과 같은 자료의 활성 기준을 확인합니다. 과거 승인·합격이
현재 조건에 유효하지 않으면 재검토·재판정 필요로 표시하고, 조회 실패는 미검토·미지정과 구분합니다.
RAG은 검색·답변·인용 세 판단을 함께 요약합니다. 기준이 다른 실행이면 해당 실행으로 연결합니다.
선택 변경·새로고침 때 이전 승인 표시를 제거하고 진행 중 조회를 취소합니다. 다른 화면에서 검토를
저장한 뒤 상단 새로고침으로 갱신할 수 있으며, 이 화면은 승인·판정·기준을 자동 저장하지 않습니다.
기존 `#new-evaluation`, `#evaluation-budget`, `#evaluation-schedules` 링크는 해당 전용 화면으로 연결합니다.
새 평가의 **평가 자료**는 서버의 용도 설명에 따라 **실제 품질 평가용·개발 검증용·과거 자료**로
묶어 보여줍니다. 선택하면 질문 수, 평가 목적, 사용 자료, 평가 범위와 한계를 확인할 수 있습니다.
자료 분류는 검토 승인이나 품질 합격을 뜻하지 않습니다. 이전 서버에서 설명을 제공하지 않은
자료는 **분류 확인 필요**로 표시하며, 기존 자료 선택·저장 요청과 실행 조건을 유지합니다.
새 평가의 **평가 모델**은 서버가 내려준 허용 목록에서 고릅니다. 기본 목록은 `gpt-6-luna`,
`gpt-6-sol`, `gpt-5.6-luna`이며 운영 설정으로 조정할 수 있습니다. 모델을 바꾸면 전송 자료·호출
예산 확인을 다시 받아 선택한 모델의 실행 설정으로 접수합니다. 접수 응답이 유실된 요청은 모델과
실행 설정을 그대로 보존해 재시도하며, 기존 모델이 목록에서 사라졌다고 다른 모델로 바꾸지 않습니다.
대시보드의 **측정 모델**은 저장된 결과를 조회하는 필터이고, 새 평가의 **평가 모델**은 실행 대상입니다.
측정 모델 목록에는 서버의 허용 모델도 포함합니다. 조회 범위에 실측 결과가 없는 모델은 **미측정**으로
표시하며, 선택해도 점수를 생성하거나 평가를 접수하지 않습니다. 허용 목록에서 빠진 과거 실측도 조회할 수 있습니다.
선택한 모델·자료·기간의 **저장된 실측 건수**는 필터 아래에 표시합니다. **전체 저장 평가 이력**은
필터 전의 모든 모델·재평가·복원 이력을 포함하며, `처리 완료`는 이 PC의 신규 모델 호출 횟수가 아닙니다.
[LLMOps 개발 환경](../../infrastructure/llmops/README.md#django-운영-화면)의 Django·Prefect·평가 실행기를
Core API와 함께 켠 뒤 저장소 루트에서 Node 24.x/pnpm 11.22.x로 `pnpm dev:web`을 실행합니다.
[운영 화면](http://localhost:5173/ops/evaluations)은 **기존 프로젝트의 관리자 계정**으로 로그인합니다.
비로그인 상태면 기존 `/login?next=/ops/evaluations`로 이동하고 로그인 후 원래 Ops 화면으로 복귀합니다.
기존 웹의 관리자 회원 관리 화면에도 **LLMOps 운영** 링크가 있습니다.

자료에서 **전체 RAG · 합성 다중 청크 캡처 재계산**을 선택하면 합성 3사례의 검색 재현율·답변 인용
재현율·상태 일치율과 측정/대상 수, 원본 실패를 확인할 수 있습니다. 새 검색·임베딩·모델 호출은
없으며 실제 모델 품질 측정이 아닙니다. 등록된 호출 계획이 있는 자료는 별도 활성화·예산 확인 후
고정 원문·청크로 새 RAG 실행을 접수할 수 있습니다. 자료·사례 검토와 품질 판정·기준 지정도
제공하지만 합성·무료 대역 결과는 현재 모델의 합격·비교 기준으로 승격하지 않습니다.
[입력·결과·복구 계약](../../backend/ops-service/README.md#전체-rag-저장-캡처-재평가)을 따릅니다.

- 화면: 운영자 로그인·로그아웃, 평가 자료·기준/후보 선택, 실행 이력/페이지 이동, 자동 상태 조회, 결과 요약·지표 차이·보고서 링크

- 목록 조회 실패 시 기존 결과와 오류를 함께 유지. 상태 반영은 별도 `ops-sync`가 수행하므로 상세 방문이 필요 없음
- 누적 예산과 실행별 장부는 15초 간격으로 읽기 조회. 미설정·과거 예약 누락·사용량 미확인을 0으로 표시하지 않음
- 새 응답 생성의 **실행 설정·예산 점검**으로 선택한 자료의 최대 호출·입력·출력 예약량과

  자료/프로필 변경·재점검 시 이전 결과를 지우고 지연 응답을 무시합니다. 설정이 바뀌면
  새로고침을 요청합니다. 예산 관련 차단/주의에는 **누적 예산 관리로 이동** 링크를 표시합니다.
  같은 화면에서 한도 저장이나 과거 사용량 반영이 성공하면 이전 점검 결과와 진행 중인 조회를
  초기화합니다. 다시 점검 버튼을 눌러 확인하며, 다른 운영자의 변경은 자동 감지하지 않습니다.
  점검 성공은 유료 전송 동의·실제 접수·품질 승인이 아니며,
  기존 접수 재시도와 승인 확인을 대신하지 않습니다. API 연결·실행기 가동·비교 기준 검토는 별도입니다.
- 전체 예산의 **미반영 실행 목록 확인 → 사용량 확인**으로 예약·사용량 반영 기록이 없는 실행을
  25건씩 조회하고 저장 자료의 전체 사용량·반영 조건·검증 실패 사유를 확인합니다. 목록과 미리보기는
  사용자가 열 때 GET으로만 조회하며 장부 반영·한도 변경·모델 호출은 하지 않습니다.
  예상 합계와 실제 반영을 구분하고 다른 실행 선택·페이지 이동·새로고침 시 이전 검증값을 지웁니다.

- **누적 한도 설정 → 변경 내용 확인 → 확인한 한도 저장**으로 호출·입력·출력 누적 한도를 설정합니다.
  **사용량 확인 → 검토 사유와 출처 확인 → 검토한 사용량 반영**으로 과거 사용량을 반영합니다.

  다른 운영자의 한도 변경, 검토 후 증거 변경, 한도 부족은 자동 적용하지 않고 오류를 표시합니다.
  응답 유실 시 같은 요청 UUID로 재확인하며 CLI 이력은 인증된 관리자 기록과 구분합니다.
  새 모델 호출이나 live 활성화는 하지 않습니다. 쓰기 API와 `0025_admin_budget_writes`가 필요하며
  한도 버전이 없는 구형 서버에서는 한도 설정 버튼을 표시하지 않습니다.
- **일별 한도 설정 → 일별 변경 내용 확인 → 확인한 일별 정책 저장**으로 서울 날짜별 호출·입력·출력
  한도를 설정·변경하거나 일별 제한만 해제합니다. 변경 전후 값과 사유를 확인한 후에만 POST하며,
  누적 한도·기존 사용량은 유지합니다. 초기 한도를 임의로 채우거나 live 실행을 활성화하지 않습니다.
  열어 둔 사이 다른 정책 변경이 조회되면 저장을 막고, 409에서는 입력을 보존한 채 재조회·재작성을
  요구합니다. 통신 응답 유실은 같은 UUID·내용으로 재확인하며 이후 정책을 되돌리지 않습니다.
  저장 성공 시 실행 전 점검과 진행 중인 점검 조회를 초기화합니다. 페이지 이탈 이후 복원은 지원하지 않습니다.
  일별 이력의 `CLI`와 인증된 `CORE_ADMIN` 변경자를 구분하며, 새 쓰기 API와 Ops migration
  `0027_admin_daily_budget_writes`가 필요합니다. `daily.limits_revision`이 없는 이전 서버에서는
  일별 설정 버튼만 숨기고 기존 예산 조회를 유지합니다.
- 호출별 장부에 `answer:{case_id}` 작업 ID를 표시. 과거 null/누락은 작업 식별 기록 없음으로 표시하며
  호출 순서로 사례를 추정하지 않음. 최신 API는 Ops `0019_embedding_usage_receipt`까지 적용 필요

- **평가 기준 자료 검토**는 AI 작성 기대 상태·인용·필수 사실·금지 주장에 대한 사람 검토이며 후보 답변 판단과 분리
- 확인·사유·자료/검토 버전으로 자료 검토를 저장하고 **현재 근거로 품질 판정 저장**으로 무료 판정. 원본 AI 작성 출처와 자동 의미 충실도 미측정은 유지
- 자료·정책·검토 변경 시 이전 판정을 이력으로 보존. 유효한 품질 합격과 최신 전체 승인이 있어야 새 비교 기준 지정 가능
- 검토 저장은 현재 검토 버전·자료/응답 해시를 전송. 응답 유실 시 같은 내용으로 재시도하며,
  409 충돌 때 입력을 유지하고 최신 검토 기록을 재조회하기 전까지 저장·품질 판정·기준 변경을 잠급니다.
- 고정 근거 상세의 **검토 새로고침**은 미저장 사례 판단·기준 자료 검토·전체 의견 또는 확인 항목이 있으면
  **계속 작성 / 입력 버리고 새로고침**을 표시합니다. 명시적으로 버릴 때만 초안과 확인을 초기화하며,
  조회 중 또는 조회 실패 후에는 이전 자료로 저장하지 못합니다. 성공한 재조회 후 내용을 다시 확인하고 입력합니다.
  기준 자료 검토 초안이 있으면 먼저 해당 검토를 저장하거나 입력을 비워야 다른 검토·판정·기준 변경을 진행할 수 있습니다.
  이 보호는 검토 패널의 새로고침에 적용하며, 브라우저 새로고침·페이지 이탈 후 초안 복원 기능은 아닙니다.
- 저장하지 않은 사례 판단이 있으면 전체 승인·기준 지정 차단. 기존 전체 승인은 사례별 판단으로 소급 변환하지 않고 재검토 필요 표시
- 검토 기준은 다음 평가의 기준 선택에 표시. 새 검토로 기준을 해제해도 이전 평가의 기준 명세는 보존
- 기준·후보의 모델·프롬프트·캡처 식별자와 원본/비교 사례 범위를 표시. 미측정 토큰·의미 충실도는 0으로 계산하지 않음
- 통신 실패 후 재시도는 요청 UUID와 선택한 자료·기준·후보를 유지. 같은 탭의 관리자별 `sessionStorage`에 명세를 보관해 새로고침·재로그인 뒤 기존 요청부터 조회
- 보관 요청은 자동 재접수하지 않으며 404일 때도 같은 요청 재확인을 눌러 전송. 다른 관리자 계정으로 재사용하지 않고 저장소 오류·손상은 접수 차단. 탭 종료·저장소 삭제 이후 복원은 보장하지 않음
- 기준 지정·해제는 확인한 버전을 전송하며 오래된 화면은 충돌로 처리. 의견을 사유로 명시적인 기준 해제와 데이터셋 기준 변경 이력 확인 가능
- 평가 상세의 **Evidently 보고서**는 React 해설 화면을 새 탭으로 엽니다. 저장된 비교 기록과 질문·답변을 읽어 자료·모델·측정 범위를 표시하며 추가 모델 호출은 없습니다. 후보만 측정된 지표도 표시하고, 미측정은 0점과 구분합니다. 합성 결과·테스트 대역·동일 기록 비교는 모델 성능 개선으로 해석하지 않도록 안내합니다.
- 원본 Evidently HTML은 기존 인증 API·무결성 검증·sandbox 보안 정책을 유지하며 해설 하단에서 새 탭으로 엽니다. 비교 기록이 없는 과거 실행은 원본을 안내하며, 질문 자료 조회 실패는 별도로 표시합니다. Langfuse·Prefect의 자체 UI는 해당 링크로 이동합니다.

개발 프록시는 정적 배포에 포함되지 않습니다. 운영 환경에는 `/ops/*` SPA 라우팅과
`/api/v1/ops/*` → Django 프록시를 별도로 연결해야 합니다. Vercel 미들웨어는
`GOVBIZ_OPS_PROXY_ENABLED=true`를 설정하기 전 Ops 요청을 503으로 반환합니다.
활성화 전 [EKS API 연결](../../infrastructure/eks/api-entrypoint.md)의 경로 분기·인증·CSRF를 확인합니다.

Kubernetes용 [Dockerfile](Dockerfile)은 정적 번들과 [Nginx](nginx.conf)를 한 이미지로 빌드합니다.
`/ops/*`를 포함한 SPA 새로고침과 같은 origin의 Core·Ops API를 처리하며, Vercel 미들웨어나
Vite 개발 서버를 실행하지 않습니다. 기존 서비스 Chart를 사용하는
[빌드·배포 안내](../../infrastructure/gitops/docs/web-kubernetes.md)를 따릅니다.
개인 환경의 실제 웹 주소 전환은 이 이미지의 CI·발행·배포 후 별도로 확인해야 합니다.

### Mac Kubernetes 백엔드에 연결

준비된 portfolio 클러스터가 있을 때, 통합 저장소 루트의 터미널에서 먼저 실행합니다.
[통합본 GitOps 연결 제한](../../infrastructure/gitops/README.md)을 확인하세요. 새 clone만으로 클러스터가 만들어지지는 않습니다.

```bash
kubectl --kubeconfig infrastructure/gitops/.local/portfolio/kubeconfig --context kind-govbiz-portfolio \
  -n govbiz-msa port-forward --address 127.0.0.1 service/core-service 18080:8080
```

다른 터미널의 이 디렉터리(`frontend/web`)에서 Node 24.x/pnpm 11.22.x로 실행합니다.

```bash
pnpm dev:k8s
```

`http://localhost:5173/?mode=filter`로 접속합니다. Kubernetes Core의 기본 허용 Origin이
`http://localhost:5173`이므로 주소의 `localhost`를 그대로 사용합니다. 웹은 Mac에서 실행되고
`/api` 요청만 Vite → loopback port-forward → Kubernetes Core로 전달합니다. 웹 자체를 Kubernetes에
배포하거나 Vercel 설정을 바꾸는 명령이 아닙니다.

이 모드는 `.env*`와 상속된 `VITE_*`를 사용하지 않고 같은 origin API·도우미 AI 비활성·카카오 링크
비활성을 고정합니다. 외부 접속을 받지 않으며 기존 Compose를 다시 켤 필요도 없습니다.
백엔드에서도 꺼진 개발 로그인 버튼은 이 모드에서 숨깁니다.
두 터미널에서 Ctrl-C로 종료합니다. Core Pod가 교체되어 port-forward가 끊기면 첫 명령을 다시 실행합니다.
새 클러스터는 빈 목록으로 시작합니다. 외부 API 비용 없이 필터·파트너·로그인을 시연하려면
[Mac Kubernetes 무료 데모](../../docs/portfolio-demo.md)를 명시적으로 입력합니다.
메일·소셜 로그인·유료 AI까지 검증한 환경은 아닙니다.

### 개인 Kubernetes의 Core·Ops 함께 연결

개인 포크에서는 [웹 연결 안내](../../docs/local-fork-development.md#4-웹-개발)의
`fork_cluster.py web`으로 소유권을 확인한 Core·Ops를 함께 연결합니다.
Compose Ops와 포트가 겹치면 `web --core-port 28080 --ops-port 28001`과
`K8S_CORE_PORT=28080 K8S_OPS_PORT=28001 pnpm dev:k8s`를 각각 실행합니다.
후자는 Bash/WSL 구문이며 PowerShell 구문은 연결 안내에 있습니다.
`dev:k8s:connected`도 같은 포트 설정을 지원합니다.
기본값은 Core `18080`, Ops `18001`이며 웹 주소는 `http://localhost:5173`을 유지합니다.

숫자 포트만 서버에서 읽고 같은 origin API·loopback 바인딩·CSRF Host 보존을 유지합니다.
잘못된 값·중복 포트는 시작을 차단하며 일반 `dev`/Compose 프록시에는 영향을 주지 않습니다.
개인 환경의 [Ops 활성화](../../infrastructure/gitops/docs/ops-runtime.md)는 별도로 필요합니다.

개인 Core에서 개발용 로그인을 별도로 승인·활성화한 경우에만 `K8S_DEV_LOGIN=true`로
관리자·회원 테스트 로그인 버튼을 표시할 수 있습니다. 기본값은 `false`이며 `true`/`false` 이외 값은 거절합니다.
이 옵션은 웹 표시만 바꾸고 Core 설정·계정·비밀번호를 만들거나 수정하지 않습니다.
Core의 `ACCOUNT_DEV_LOGIN_ENABLED=true`와 개인 Secret의 개발 계정 비밀번호는 별도로 준비해야 합니다.
Kubernetes 재적용으로 Core의 기본값 `false`가 복원되면 버튼을 눌러도 로그인에 실패합니다.

```powershell
# 저장소 루트, 이미 Core·Ops 포트 전달을 실행한 개인 PC
$env:K8S_CORE_PORT='28080'
$env:K8S_OPS_PORT='28001'
$env:K8S_DEV_LOGIN='true'
pnpm --dir frontend/web dev:k8s
```

Bash/WSL에서는 `K8S_CORE_PORT=28080 K8S_OPS_PORT=28001 K8S_DEV_LOGIN=true pnpm --dir frontend/web dev:k8s`를 사용합니다.
Kubernetes 모드의 `.env`·상속된 `VITE_*` 차단과 loopback 바인딩은 유지하며,
`build` 결과에는 이 옵션을 켜더라도 개발 로그인 버튼을 포함하지 않습니다.

### 일반 네이티브 웹 개발

Node.js `24.x`, pnpm `11.22.x`가 필요합니다. Core API와 검색에 필요한 MySQL·AI Service·Qdrant는
[Core API 실행 안내](../../backend/core-service/README.md)에 따라 먼저 실행합니다.

```bash
# 저장소 루트에서 설치합니다. lockfile은 루트 하나만 사용합니다.
pnpm install --frozen-lockfile
pnpm dev:web
```

기본 API 주소는 `http://localhost:8080`입니다. 다른 주소를 사용하려면 `frontend/web/.env.example`을
`frontend/web/.env.local`로 복사하고 `VITE_CORE_API_BASE_URL`을 변경합니다. `VITE_` 값은 브라우저에
노출되므로 비밀값을 넣지 않습니다. API를 다른 origin으로 직접 호출할 때는 Core API의 CORS 설정도
프론트엔드 접속 주소와 맞춰야 합니다.

`VITE_CORE_API_BASE_URL=/`이면 Vite의 `/api` 프록시를 사용합니다. 프록시 목적지는
`VITE_DEV_PROXY_TARGET`이며 기본값은 `http://localhost:8080`입니다. 이 프록시는 개발 서버 설정으로,
정적 빌드 배포 시에는 별도의 `/api` 라우팅과 SPA 경로 처리가 필요합니다.
배포용 빌드에서는 `VITE_CORE_API_BASE_URL`을 반드시 지정합니다. 같은 origin에서 API를 제공한다면
`/`, 별도 서버라면 브라우저가 접근할 수 있는 공개 API 주소를 사용합니다.

`VITE_KAKAO_CHANNEL_ID`에 카카오톡 채널 공개 ID(`_`로 시작)를 넣으면 도우미 빠른 답변에 "담당자에게 문의"가 생기고,
누르면 `https://pf.kakao.com/<ID>/chat` 1:1 채팅을 새 탭으로 엽니다. 비워 두면 문의 항목을 보여 주지 않습니다.
Compose에서는 루트 `.env`의 `KAKAO_CHANNEL_ID`가 이 값으로 전달됩니다.

`VITE_ASSISTANT_AI_ENABLED=true`(Compose는 루트 `ASSISTANT_AI_ENABLED`)일 때만 도우미가 자유 입력을 AI로 보냅니다. 기본은 꺼짐이며,
꺼져 있으면 자유 입력은 "아래 주제 중 하나를 골라 주세요"로 돌려보내고 주제·상태·카카오 문의 알약만으로 동작해 모델 비용이 들지 않습니다.
Core의 도구 에이전트(`ASSISTANT_AGENT_ENABLED`)가 켜져 있으면 같은 응답에 `cards[]`(모집글·공고: 제목 링크, 부제, 고른 이유, 관심 공고 질문의 원문 인용)가 함께 오고
`PARTNER_MATCH`·`SAVED_PROGRAMS_QUESTION` 의도가 추가됩니다. 화면은 카드가 오면 목록 행(제목을 누르면 상세 화면)으로 그리고 "AI 생성 · …" 출처를 붙이며,
없으면 지금처럼 동작합니다. 프런트 스위치는 그대로입니다.

도우미 대화는 계정 소유자와 함께 탭 `sessionStorage`에 저장하고, 인증 확인 뒤 같은 계정의 캐시만 복원합니다.
로그아웃·로그인·계정 전환은 Redux auth 이벤트로 대화·빠른 답변·저장소를 초기화합니다. 패널의 작성 중 입력도 닫으며,
같은 계정 재로그인을 포함해 이전 세션의 AI·관심 공고 조회 응답은 표시하거나 다시 저장하지 않습니다.
소유자 정보가 없는 구버전 캐시는 사용하지 않습니다. AI 자유 질문에는 현재 세션의 최근 대화 최대 6개가 전송됩니다.

## 화면과 현재 동작

### 직접 필터 검색

`/`와 `/app/chat`의 검색 방식 탭에서 **AI 대화 검색** 또는 **필터 검색**을 선택합니다.
기본은 기존 AI 대화이며 탭 전환만으로 AI 검색을 실행하거나 대화를 초기화하지 않습니다.
정보가 부족하면 “조금만 더 알려주세요” 카드의 “추가 내용 입력하기”로 검색 입력창에 연결합니다. 기존 대화·추가 질문·작성 중인 입력은 유지하며, 보충 내용 전송 후 조건을 확인해야 검색합니다. 검색할 조건이 준비된 카드의 제안 취소는 그대로 제공합니다.

- 필터 검색은 공고명·기관명 키워드, 지역·분야, 출처(전체·기업마당·K-Startup·과학기술정보통신부·충청남도 온라인수출지원시스템), 접수 상태를 선택하고 **검색**으로 적용합니다.
- 지역·분야는 펼쳐진 단일 선택 목록으로 표시합니다. 선택 항목을 녹색으로 강조하며 키보드 방향키로 이동할 수 있습니다.
  기본 지역 18개·분야 18개(기업마당·K-Startup 분류의 합집합)와 각 ‘전체’ 버튼은 첫 화면부터 표시하고, 서버에 추가 분류가 있으면 중복 없이 덧붙입니다.
  조회 중·실패·0건이어도 기본 버튼과 편집 중인 선택은 유지합니다. 로딩·오류 안내와 **다시 불러오기**는 결과 영역에만 표시합니다.
- K-Startup을 선택하면 접을 수 있는 **추가 조건**에서 창업 업력·신청 대상·대표자 연령을 고릅니다.
  공식 기본 선택지에 서버 전체 K-Startup 공고의 선택지를 합치며, 검색 결과가 적어도 선택지는 줄이지 않습니다.
  출처를 전체 또는 다른 제공처로 바꾸면 전용 조건을 비웁니다. 추가 조건 역시 공고 분류이며 신청 자격 판정이 아닙니다.
- 과학기술정보통신부(`MSIT`)·충청남도 온라인수출지원시스템(`CNTRADE_NOTICE`)에서 구조화된 접수 기간이 없는 공고는
  **상태 확인 필요**로 조회합니다. 해당 출처를 고르면 전체·상태 확인 필요 검색 안내를 표시하되, 사용자가 선택한 접수 상태를 자동으로 바꾸지 않습니다.
- `CNTRADE_NOTICE`는 개별 상세 URL이 없어 카드·상세의 **공식 공지 목록** 링크로 이동합니다.
  목록에서 공고 제목으로 해당 공지를 확인해야 하며, API 원본 ID로 개별 상세 링크를 추정하지 않습니다.
- 최초 접수 중 목록, 최신순·마감일순, 12개씩 페이지 이동과 초기화를 제공합니다. 최신순은 제공처의 수정 시각을
  우선하고 등록 시각을 보조로 사용한 기존 정렬 값 기준입니다.
- URL에 비어 있지 않은 적용 조건과 페이지를 보존하며 새로고침·뒤로 가기·상세/원문 질문 왕복 시 복원합니다.
  로그인 상태로 공개 필터 URL을 열어도 조건을 유지한 채 `/app/chat`으로 이동하며, 내부 상세·질문에서는 사이드바를 유지합니다.
- 편집 중인 필터는 검색 전까지 적용하지 않습니다. 지역·분야는 제공처 분류와 정확히 일치하는 값으로 조회하며,
  버튼이 있어도 해당 공고가 없으면 0건일 수 있습니다. 지역 ‘서울’에 ‘전국’을 자동 포함하지 않습니다. 태그 필터는 기업 자격 판정이 아닙니다.
- `BrowseSupportProgramsUseCase → Repository → GET /api/v1/support-programs/catalog`로 조회합니다.
  해석·임베딩·랭킹·검색 준비 상태에 의존하지 않으며 AI 실패를 우회하는 자동 fallback도 아닙니다.
- 목록 조회에는 AI 점수·자격 확인 배지가 없습니다. 실제 신청 요건은 상세·원문에서 확인합니다.
- 요청은 탭을 떠나거나 조건이 변경되면 취소하고 늦은 응답을 무시합니다. 10초 제한과 수동 재시도를 제공하며,
  오류를 정상 0건으로 표시하지 않습니다.

필터 탭을 사용하려면 새 Core 목록 API도 반영돼 있어야 합니다. 공개 API와 서버 필터 계약은
[직접 조건 검색](../../docs/support-program-catalog.md)에 정리했습니다.

### 전체 화면

공개 검색(`/`)은 공용 헤더와 가로 검색 탭을 유지하며, 첫 메시지를 보내면 본문만 대화 영역과 하단 입력창으로 바뀝니다(세션 목록·보조 패널 없음).
나머지 공개 화면은 공용 헤더를, 로그인 뒤 `/app` 화면은 작업 사이드바를 사용합니다.
로그인한 사용자가 공개 URL(`/`, `/pricing`, `/partners`, 공고 상세)에 오면 같은 내용의 `/app` 화면으로 보내고, 비로그인으로
`/app`에 오면 `/login?next=`로 보냅니다. 세션을 확인하는 동안에는 리다이렉트하지 않고 빈 화면 대신 확인 중 표시(`role="status"`, 300ms 뒤 스피너)를 둡니다. 로그인·회원가입·비밀번호 찾기·재설정은 둘 다 쓰지 않는 단독 화면(상단 로고와 가운데
카드)이며 로그인 상태에서는 작업 화면으로 돌려보냅니다. `/app/admin/accounts`(회원 관리)는 관리자만 엽니다. 경로 상수와 공개↔내부 대응은 `presentation/shared/routes/appPaths.ts`에 있습니다.

아래 안내 문구로 갈음하고 서버가 가입 시각을 기록합니다.

예시 모집글로 API를 대신합니다. 제안은 `PartnerProposalRepository`(`data/api/partnerProposalApi`)로 보내기·수락·거절·철회·제안함을 읽고,
받은 제안함은 사이드바 배지·제안함 화면·모집글 상세가 함께 읽고 제안함 화면이 수락·거절로 바꾸므로 `presentation/shared/partner-proposal`의
Redux `receivedProposals` slice와 `useReceivedProposals`(계정당 한 번 조회, 결과를 slice에 반영)가 소유하고,
보낸 제안함은 제안함 화면만 쓰므로 `useSentProposalBox`의 Hook 로컬 상태로 둡니다.
추천·매칭은 아직 **데모 단계**라 ViewModel이 예시 값을 돌려줍니다. 관리자 계정 관리는 Core의 `/api/v1/admin/accounts`를 씁니다.
지역은 공고 분류와 같은 `domain/entities/Region`의 시·도 목록을 쓰고, 프로필의 정식 명칭은 `toRegionName`으로 바꿉니다.
모집글 작성·프로필 일치 표시는 `useAuthSession().hasCompany`(기업 등록 여부) 하나로 정하며, 제안 조건(이메일 인증)은 서비스 정책이라 작성자가 고르지 않습니다.
모집 작성은 `SavedSupportProgramPickerDialog`·`useSavedSupportProgramChoices`(신청 문서·중복 검토의 공고 고르기 패널도 같은 관심 공고 조회 훅을 씀)로 관심 공고함을 팝업에서 읽어 접수 중인 공고 1개를 고르고
`createPartnerRecruitmentUseCase`로 등록합니다. 관심 공고는 화면 진입이 아니라 팝업을 열 때 조회하며, 접수 중이 아니거나 오늘 접수가 끝나는 공고는 팝업에서 이유(`접수 중 아님`·`오늘 접수 마감`)와 함께 비활성입니다.
공고 카탈로그 검색은 모집글 작성에서 쓰지 않으며, 담은 공고가 없으면 관심 공고함 링크로 안내합니다.
공고당 모집글은 하나이며 마감일은 접수 마감 전날까지입니다. 모집글 저장·숨김·신고·회원 정지 등
연결되지 않은 동작은 준비 중으로 비활성화했습니다. 프로필의 선택은 화면 안에서만 유지되고 추천에 전달되지 않습니다.
없는 `recruitmentId`는 다른 모집글로 대체하지 않고 "찾을 수 없습니다"로 보여 줍니다.
공개 파트너 모집 화면은 `presentation/features/public-partner-recruitment`에 따로 두어 매칭·제안 폼 없이 읽기만 제공하고,
두 파트너 feature가 함께 쓰는 조회 훅과 표시 helper는 `presentation/shared/partner-recruitment`에 둡니다.
관심 공고함은 `/api/v1/me/saved-programs`를 쓰며 공고 상세의 관심 공고 저장 버튼(비로그인은 로그인 링크)과 모집글 상세의 `관심 공고에 추가` 버튼이 담습니다.
두 버튼은 `presentation/shared/support-program/useSupportProgramSaveViewModel`을 함께 씁니다.
로그인한 사용자는 AI 검색 결과 카드의 자격 배지 앞 `관심` 버튼에서도 담기·해제를 할 수 있습니다.
`useSearchResultInterests`가 결과 표시 시 관심 목록을 한 번 읽고 기존 조회·저장·해제 UseCase를 사용합니다.
한 대화에서 반복되는 같은 공고는 제공처 코드·원본 ID 기준으로 상태를 공유하며, 조회·변경 중 중복 요청을 막고 실패 시 재시도 안내를 표시합니다.
로그아웃·계정 변경 시 이전 요청을 취소하고 이전 계정의 상태를 노출하지 않습니다.
진행 관리는 기존 신청 준비 목록 API를 재사용하며, 각 건의 독립된 진행 revision으로 단계 변경을 저장합니다. 로그인 작업 사이드바는 흰색 배경과 둥근 메뉴 항목을 사용하며,
선택 메뉴는 연한 초록색 배경·초록색 글자, 준비 중 메뉴는 연한 회색 배경·알약 모양 배지로 구분합니다.
`지원사업 새검색`은 돋보기 아이콘으로 표시하며 기존 대화·조건 초기화 동작을 유지합니다.
메뉴 순서는 사용 빈도와 업무 흐름(찾기 → 모아두기 → 준비·검토 → 협업 → 결제)을 따라 지원사업 새검색 → 관심 공고함 → 기업 맞춤 리포트 → 신청 문서 작성 →
중복 지원·수혜 검토 → 파트너 관리 → 요금제이며 무리 이름 없이 한 목록입니다. 제안함은 파트너 관리의 탭이고 받은 제안 대기 건수 배지는 파트너 관리 메뉴와 제안함 탭에 붙습니다. 도우미 도움말 주제 순서와 맞추며 가나다순은 쓰지 않습니다.

### 로그인 회원의 대화 기록

로그인 작업 사이드바의 `요금제` 아래에 대화 기록을 표시합니다. 첫 전송한 질문을 제목으로 한 대화에 질문·답변·
미확정 제안·확정 검색 조건·결과를 누적하고, `지원사업 새검색` 후 다음 질문을 전송하면 별도 기록을 만듭니다.
비로그인 대화와 미전송 초안·빈 새 대화는 저장하지 않습니다. 기록은 기존 MySQL의 `chat_conversation`에 계정별로
저장하므로 새로고침·재로그인·다른 기기에서도 목록에서 다시 열 수 있습니다. 새 접속 시에는 빈 채팅에서 시작합니다.
목록은 생성 순서의 최신 30개를 먼저 조회하고 `이전 기록 더 보기`로 이전 기록을 추가합니다.

흐름은 `useWorkspaceLayoutViewModel/useChatHistory → ChatConversationUseCase → ChatConversationRepository → data/api → Core API`입니다.
기록을 열면 Redux 대화 상태를 복원하고 AI 탭으로 이동합니다. 조회·복원만으로 해석·검색·OpenAI를 호출하지 않습니다.
기록의 공고 결과는 저장 당시 내용이며 현재 상태·신청 조건은 원문에서 다시 확인하도록 안내합니다.
중단된 요청은 로딩 대신 명시적인 재시도 안내로 복원하며, 새 대화·기록 전환 시 이전 요청의 늦은 응답을 섞지 않습니다.

저장은 대화별로 직렬화하고 최신 변경을 이어서 반영합니다. 실패 시 현재 창의 내용을 유지하며 저장 오류와 수동 재시도를
표시합니다. 다른 창의 변경은 `expectedVersion` 충돌(409)로 거절하며 강제로 덮지 않습니다. 충돌 시 현재 내용을 별도로
보관한 뒤 새로고침하여 서버 기록을 다시 확인해야 합니다. 미저장 상태에서 창을 닫거나 로그아웃하면 확인을 요청합니다.
한 대화는 메시지 200개·UTF-8 JSON 2,000,000바이트 이내이며 초과분을 조용히 잘라 저장하지 않습니다.
각 기록 오른쪽 휴지통 버튼 → 앱 안 삭제 확인 대화상자(`WorkspaceModal`, danger)에서 삭제를 누르면 대화를 개별 삭제합니다.
삭제는 되돌릴 수 없으며 성공 후 목록에서 제거하고 포커스를 새검색으로 옮깁니다.
현재 보고 있는 대화를 삭제하면 빈 새 대화로 초기화하고, 다른 대화의 삭제는 현재 화면 내용을 바꾸지 않습니다.
삭제 중 중복 클릭을 막고 실패 시 목록·현재 대화를 유지한 채 재시도를 안내합니다. 늦은 목록·상세·자동 저장 응답이나
다른 탭의 저장 요청은 삭제한 대화를 되살리지 않습니다. DB에서도 제목·스냅샷은 비우고 재저장 차단용 식별 정보만 남깁니다.
대화 삭제는 AI·검색 API를 호출하지 않으며 공고 원본·다른 업무 문서를 삭제하지 않습니다. 이름 변경은 아직 제공하지 않습니다.
계정 탈퇴 시에는 개인 대화 기록과 삭제 식별 정보를 함께 제거합니다.

`src/test/setupChatHistory.ts`는 다른 기능 테스트의 순차 fetch 대역과 백그라운드 기록 API를 격리합니다. `src/test/setupPlanUsage.ts`는 여러 화면이 백그라운드로 읽는 이용량 API를 같은 이유로 격리합니다. `src/test/setupPreparationJobs.ts`는 작업 화면 틀이 사이드바 배지를 위해 읽는 분석·초안 작업 목록(`PreparationJobsSync`)을 같은 이유로 격리하며, 그 동작을 검증하는 테스트는 mock을 해제합니다.
`App.chatHistory.test.tsx`와 `ChatConversationRepositoryImpl.test.ts`는 이 대역을 해제하여 실제 HTTP·DTO 경로를 검증합니다.
Core API 코드도 변경되므로 기존 실행 이미지는 재빌드해야 합니다. [백엔드 변경 반영 안내](../../infrastructure/README.md#백엔드-변경-반영과-화면api-버전-불일치)를 참고하세요.

신청 문서 작성 도우미는 `View → ViewModel → ApplicationPreparationUseCase → ApplicationPreparationRepository →
data/api → Core API` 흐름을 사용합니다. 새 작성 화면은 [공고 고르기]로 여는 오른쪽 `공고 고르기` 패널(공용 `presentation/shared/support-program/ProgramPickerPanel`,
중복 지원 검토 1단계와 같은 컴포넌트)의 관심 공고함 · 전체 검색 탭에서 공고 1개를 고릅니다. 전체 검색은 기존 공고 카탈로그의 모든 제공처를 공고명·기관명과
지역·지원 분야·출처·접수 상태 필터로 찾고, 공식 첨부 수집을 검증한 기업마당·K-Startup·과기정통부·충남 수출지원 공고를 선택하는 흐름을 기본으로 제공합니다.
관심 공고는 새 작성 화면 진입만으로 조회하지 않고 패널을 열 때 불러오며, 행을 고르면 그 공고의 저장된 양식을 조회(AI 호출 없음)하고 조회를 마쳐야 [이 공고 선택]을 누를 수 있습니다.
K-Startup은 카탈로그의 공식 상세 URL과 공고 ID를, 충남은 OpenAPI 제목·본문과 공식 게시판 상세의 단일 일치를 검증한 뒤
PDF/HWP/HWPX 첨부를 분석합니다. 검색에서 찾지 못한 기업마당 공고만 공식 URL·ID 직접 입력을 보조 경로로 제공합니다.
공고 선택은 분석을 시작하지 않으며 사용자가 `신청 문서 찾기`를 누를 때만 `/forms/discovery-jobs`에 UUID 요청 키와 공고를 POST합니다.
202 접수 뒤에는 3초 간격으로 이전 GET 완료 후 상태를 다시 조회합니다. 새 작성 화면은 진입할 때 본인의 최근 20개 분석 작업을
GET으로 확인하고 가장 최근 작업을 자동 복원합니다. QUEUED/RUNNING이면 분석 중 상태와 자동 조회를 이어가고, SUCCEEDED이면
저장된 신청 문서 결과를 바로 표시합니다. 작업은 공고명·제공처·요청 시각·상태가 구분된 카드에서도 다시 선택할 수 있습니다.
조회 실패 후 재시도는 GET만, POST 응답 유실 후 같은 화면의 재시도는 같은 요청 키만 사용합니다.
UNKNOWN은 관리자 확인을 안내하며 자동 재분석하지 않습니다. [API·상태·운영 제약](../../docs/rabbitmq-application-form-discovery.md)을 참고하세요.
공고 상세 링크는 공고 식별자를 입력란에만 전달하며 화면 진입으로 분석을
시작하지 않습니다. 분석이 끝나면 공고 검색 영역을 접고 두 번째 `신청 문서 확인` 단계로 전환하며, 발견 문서·문항을 확인하고
별도 시작 버튼을 눌러야 준비 건을 생성합니다. 목록·상세는 AI Service를
호출하지 않고 `institutionReviewed=false`를 표시해 AI 추출과 기관 검수를 구분합니다.
HTTP·Repository 경계는 목록·양식 endpoint의 404 또는 상세 endpoint의 비계약 404를 구버전 API로 구분해 Core·AI 이미지
갱신을 안내합니다. 상세가 `APPLICATION_PREPARATION_NOT_FOUND`를 반환한 경우에는 기존처럼 없거나 타인 소유인 신청 준비로
안내합니다. 정상 빈 목록은 오류로 바꾸지 않고 새 작성 진입을 유지합니다. 백엔드만 안전하게 갱신하는 방법은
[Compose 실행 안내](../../infrastructure/README.md#백엔드-변경-반영과-화면api-버전-불일치)를 참고하세요.

사이드바와 각 화면의 머리말은 화면에 고정하고 본문 칸만 스크롤합니다. 작업 채팅의 입력창은 화면 아래에
붙어 있고 대화만 그 위에서 스크롤됩니다. 한 칸으로 접히는 좁은 화면에서는 고정을 풀어 문서 전체가 스크롤됩니다.

공개 검색(`/`)은 대화 전에는 기존 공용 헤더·가로 검색 탭·가운데 소개와 큰 입력창·예시 질문을 표시합니다.
초안 입력·예시 선택만으로는 화면을 바꾸거나 자동 전송하지 않습니다. 첫 메시지를 전송해도 공용 헤더와
가로 검색 탭을 유지하며, 본문만 중앙 대화 영역과 하단 입력창으로 전환합니다.
`GuestSearchLayout`(`presentation/shared/support-program`)은 비로그인 검색·공고 상세·원문 질문이 함께 쓰는 껍데기로 공용 헤더와 `SearchModeTabs`를 고정합니다.
비로그인 AI 검색에는 세션 목록을 두지 않으므로 왼쪽 `AI 대화 도구` 보조 패널(`새 AI 대화 검색`·로그인 안내)은 그리지 않습니다(`showConversationPanel={false}`, 부품은 남아 있음).
비로그인 대화의 초기화는 로고 클릭(문서 새로고침)·로그인·계정 전환뿐입니다. 파트너 모집·요금제·회원가입·로그인은 기존 공용 헤더에서도 접근합니다.
검색 방식은 대화 전후 모두 가로 탭(좌·우 화살표)이며 Home/End도 지원합니다.
검색 탭은 본문과 분리된 상단 공통 영역에서 전체 너비 기준으로 가운데 정렬합니다.
사용자 메시지는 오른쪽 회색 말풍선에, 답변과 결과는 여백 있는 본문에 표시합니다. "AI 답변은 참고용" 고지는 입력창 바로 위에 두고,

READY 수신 후에는 이전 추가 질문 문맥을 종료합니다. 후속 메시지를 입력하는 동안에도 기존 조건 제안 카드를 유지합니다.
보내지 않은 메시지가 있으면 기존 제안의 확인 검색을 막고 이유를 안내합니다. 입력을 비우면 같은 제안으로 검색할 수 있으며,
메시지를 전송하면 보관한 제안 조건을 다음 해석에 함께 전달하고 새 응답으로 제안을 갱신합니다.
제안 취소나 새 대화는 제안과 미확정 초안을 모두 무효화합니다.
`왜 못찾아?` 같은 질문에는 ANSWERED의 설명을 대화 말풍선으로 표시하며, 조건·제안을 바꾸거나 검색하지 않습니다. 해석은 공고 준비 상태와 독립적으로 허용하고 실제 확인 검색만
readiness로 차단합니다. 준비 장애·추가 질문·해석 실패·공고 0건을 서로 구분하며 단문 검색 fallback은 없습니다.
해석 API의 검증된 `504 AI_SERVICE_TIMEOUT`은 시간 초과, `503 AI_SERVICE_UNAVAILABLE`은 일시 이용 불가로
구분합니다. 서버 원문 오류를 화면에 노출하지 않으며 429·혼잡 제한, 브라우저 40초 제한, 수동 재시도는 유지합니다.
검색·해석 실패와 시간 초과는 입력창 아래 배너 대신 대화 안의 assistant 메시지로 기록합니다.
진행 중인 검색·조건 해석 요청은 채팅 화면이 아니라 스토어의 `ChatRequestRegistry`(thunk extraArgument)가 쥐고 있어 다른 메뉴로
이동해도 끊기지 않고, 결과는 Redux로 돌아옵니다. 화면 밖에 있는 동안은 검색 중인 대화의 기록 항목에 점이 붙습니다.
계정 줄 위에는 별도 검색 상태 패널을 표시하지 않습니다. 사이드바를 접었거나 모바일·공개 헤더에서는 헤더 칩이 같은 상태를 알립니다.
결과가 도착하면 오른쪽 위 헤더 아래에 한 줄 알림(12초 뒤 자동 접힘, "대화 보기"로 이동)을 띄웁니다. 몇 초면 끝나는 조건 해석은
헤더 칩에 진행 중 표시 없이 결과가 도착했을 때만 알리고(기록 항목의 점은 해석 중에도 붙음), 자유 질문 답변("답변이 도착했어요")은 알림을 끄고 배지로만 알립니다.
채팅 화면이 열리면 `outcomeSeen`으로 결과 도착 점·배지·알림을 지웁니다. 공개 헤더의 칩(`검색 진행 중`·`검색 결과 도착`)은 가운데 정렬된
이동 경로 묶음 왼쪽에 겹쳐 놓아 칩이 생기고 사라져도 `지원사업 찾기`·`파트너 모집`·`요금제`가 밀리지 않습니다(좁은 화면에서는 줄 맨 앞 항목). 요청 취소는 로그아웃·취소 버튼·90초 시간 초과, 그리고 진행 중에 검색 화면에서 사이드바의 새검색을 다시 누르거나 다른 대화 기록을
열 때(앱 안 확인 대화상자 "새 검색을 시작하면/다른 대화를 열면 진행 중인 검색이 취소되고 결과를 받지 못합니다. 계속할까요?"에서
계속을 누른 경우, 떠나는 대화는 취소 상태로 저장)에서만 일어납니다. 다른 메뉴에서 누른 새검색은 필터 검색 탭도 써야 하므로 묻지 않고
검색 화면으로만 이동해 진행 중인 대화를 보여 주고, 지금 보고 있는 대화를 다시 여는 것도 확인 없이 그대로 둡니다.
실패 기록은 후속 입력·재시도 성공 뒤에도 남고, 현재 마지막 실패 말풍선에만 다시 검색/다시 해석 버튼을 표시합니다.
재시도 중에는 버튼을 숨겨 중복 요청을 막으며, 글자 수 초과처럼 입력을 수정해야 하는 안내는 입력창에 유지합니다.
해석 응답은 필수 필드, READY/질문/ANSWERED 일관성, 실제 날짜, UTF-16 길이, 문자 규칙, 변경 필드 순서·중복을 Zod로 검증합니다.
검색 이력에는 확인한 검색 의도와 당시 조건을 복사합니다.
해석과 확인 검색은 요청 제한에서 각각 한 건으로 계산됩니다. [전체 C02 계약](../../docs/conversation-condition-update.md)을 참고하세요.

확인한 제안의 실제 검색은 기존 `POST /api/v1/support-programs/search`에
`{ query, acceptingOnly, companyConditions?: { region?, industry?, establishedOn?, foundedYear?, supportPurpose? } }`를 보냅니다.
조건은 검색어 500자에 이어 붙이지 않고 별도 JSON 필드로 전달합니다. 검색어와 충돌하면 사용자가 적용한
기업 조건을 우선하며, 미입력은 자격 충족을 뜻하지 않습니다. AI 판단은 공고 원문 확인이 필요합니다.
기업을 등록한 로그인 계정은 새 대화의 첫 메시지 전송 시 기존 회사 조회 API로 소재지·업종·설립연도를 불러와 기본 조건으로 사용합니다.
조회에 실패하면 해석을 중단하고 재시도를 안내하며, 회사 정보 없이 몰래 검색하지 않습니다. 대화에서 수정·해제한 값은 이후 요청에서 다시 덮어쓰지 않습니다. 초기 조회 실패 상태도 기록에 보존해 기록 복원 후 재시도할 수 있습니다.
비회원은 대화에서 확인한 조건만 사용합니다. 기록을 열면 당시 조건을 유지하고, 새 대화에서는 최신 등록 정보를 다시 불러옵니다.
설립연도는 선택 필드 foundedYear로 보존하고, 정확한 establishedOn과 동시에 보내지 않습니다. 조건 상세·검색 당시 표시·대화 기록에도 연도가 유지됩니다.
검색에 적용한 조건은 AI 추천에 사용되므로 개인정보·비밀정보는 입력하지 않습니다.
Core가 제공하는 기존 GET 검색 계약도 유지되지만 이 화면은 POST를 사용합니다.

검색 준비 상태는 내부에서 확인하지만 정상 `SEARCHABLE` 상태에서는 별도 안내 패널을 표시하지 않습니다.
공고 수·인덱스 준비 여부·동기화 시각·제공처별 상세 목록도 채팅 화면에서 제거했습니다. API의 필수
`sources`와 기존 응답 검증은 유지하며, 검색 가능한지 판단하는 안전장치를 없애는 변경은 아닙니다.
일부 제공처만 준비된 `SEARCHABLE_WITH_PARTIAL_SOURCES` 상태에서도 검색할 수 있으며,
초기 준비·조회 실패·검색 불가·일부 제공처 검색·이전 데이터 사용만 짧은 문구로 안내합니다.
제공처 중 초기 준비 상태가 있으면 5초마다 상태를 확인하고,
검색 불가 또는 일부 제공처만 준비된 상태에서는 사용자가 상태를 다시 확인할 수도 있습니다.
최신 동기화가 실패했지만 저장 공고로 검색 가능한 상태는 별도로 안내합니다.
상태 조회가 10초 동안 응답하지 않으면 요청을 취소하고 오류·재확인 버튼을 표시합니다.
취소된 요청의 늦은 응답은 검색 가능 상태를 덮어쓰지 않습니다.
직전 조회가 실패했다면 재확인 중에도 검색 차단을 유지하고 실제 성공 응답을 받은 뒤에만 해제합니다.
재확인 요청 중에는 안내 버튼을 비활성화합니다.

검색 결과 카드는 **서버가 반환한 순서 그대로** 표시하며 자격 `MATCH`를 앞으로 다시 정렬하지 않습니다.
`eligibilityReview`의 지원 대상·지역 판정이 모두 `MATCH`인 **조건 확인 공고**와 `UNKNOWN`이 있는
**확인 필요 공고**는 각 카드의 배지로 구분합니다. 판정 없는 기존 점수 공고도 확인 필요로 표시하며,
점수·판정이 모두 없는 최신 공고는 자격 미평가로 표시합니다. 자격 확인이 필요한 높은 관련도 공고도
낮은 관련도의 조건 확인 공고 뒤로 밀리지 않습니다.
카드는 자격 상태를 관련도 점수보다 먼저 표시하고, 두 축의 설명과 공식 API 본문 인용을
HTML 해석 없이 텍스트로 보여 줍니다. 점수·기존 관련 검색 정보·지역/분야 태그는 자격 근거가 아닙니다.
채팅 응답과 스크린 리더 안내도 조건 확인·확인 필요·최신 목록 건수를 구분합니다.
`eligibilityReview` 미제공/null은 판정 없음으로 받아들이되, MATCH 축 인용 누락, 전체·축 판정 모순,
공식 본문 외 근거 필드 및 길이 위반은 응답 검증에서 거부합니다. 설명 160자·인용 240자는
원시 Unicode 코드 포인트 기준이며, 공백은 보존하고 제어·형식문자 등 Unicode C 범주는 거부합니다.
근거 범위는 **기업마당 등 공식 API 본문 기준 · 첨부파일 미검증**이며 최종 신청 자격을 보장하지 않습니다.
검색 당시 조건 스냅샷은 현재 조건 수정이나 상세 이동으로 덮어쓰지 않습니다.
실재하지 않는 날짜, 지정한 본문에 없는 인용, 같은 제공처·원본 ID의 중복 결과, 요청과 다른 검색어의
응답도 거부합니다. 이는 비정상 응답에 대한 방어이며 클라이언트가 AI 자격 판단을 다시 수행하는 것은 아닙니다.

검색 결과에는 신청 기간·원문 링크도 표시됩니다. 상세 화면은 검색 결과의
메모리 상태에 의존하지 않고 URL의 `sourceCode`·`sourceProgramId`로 다시 조회하므로 새로고침과
직접 접속을 지원합니다. 상세 API는 검색별 점수·추천 이유·자격 판정을 제공하지 않으며,
**자격 미평가** 안내와 함께 공고 정보·현재 접수 상태를 보여 줍니다. 상세 조회를 기업 조건에 대한
재평가로 표시하지 않으며 검색 화면으로 돌아오면 기존 판정을 유지합니다.
잘못된 주소, 없는 공고, 조회 실패, 로딩 상태를 구분합니다.
일시 실패·시간 초과는 상세 화면 안에서 수동으로 다시 조회할 수 있습니다. 상세·질문 왕복에는
원래 검색 경로(`/` 또는 `/app/chat`)를 라우트 상태로 보존합니다. 두 값 외의 경로와
임의의 외부 주소는 복귀 경로로 사용하지 않습니다. 직접 진입 시 기본 복귀 경로는 `/`입니다.
원문 링크는 제공처 코드별 공식 도메인 allowlist와 `http(s)` 스킴을 함께 검증합니다. 현재
`BIZINFO`의 `bizinfo.go.kr`, `KSTARTUP`의 `k-startup.go.kr`, `MSIT`의 `msit.go.kr`,
`CNTRADE_NOTICE`의 `cntrade.chungnam.go.kr` 도메인 및 각 하위 도메인을 허용합니다.
그 외 제공처를 추가할 때는 해당 제공처의 공식 도메인을
allowlist에 명시적으로 추가합니다. 테스트용 제공처는 production 허용 목록에 포함하지 않습니다.
공고 원문 근거 질문은 현재 `BIZINFO`·`KSTARTUP`만 지원하며 화면은 서버의 `evidenceQuestionSupported`로만 판단합니다.
지원 공고 상세의 **이 공고에 질문하기** 링크로
별도 질문 페이지에 이동합니다. 질문 페이지도 URL 식별자를 검증해 직접 접속·새로고침을 지원하며,
진입만으로 상세 API나 질문 API를 호출하지 않습니다. 사용자가 질문을 제출할 때만 기존 답변 API를
호출하고, 질문·답변은 새로고침 시 초기화됩니다. 다른 제공처 상세에는 미지원 안내와 기존 원문 링크를
표시합니다. 미지원 제공처의 질문 페이지로 직접 접속해도 입력을 표시하지 않고 ViewModel에서 전송을 차단합니다.
K-Startup·과학기술정보통신부·충청남도 온라인수출지원시스템 공고도 Core 카탈로그 API를 통해 필터 검색·상세 조회합니다. 과학기술정보통신부·충청남도 공고의 원문 근거 질문은 계속 미지원입니다.
근거 링크는 서버가 준 원문 이름(`sourceLabel`)으로 "근거 N · 기업마당 상세 본문 ↗"처럼 표시합니다.
알 수 없는 제공처나 위조 URL이 응답에 포함되면 전체 응답을 거부합니다.

검색 요청에는 사용자가 확인한 검색 의도와 기업 조건을 전달합니다. C02는 현재 확정 상태·새 메시지와
필요한 경우 마지막 질문·미확정 제안과 최근 완료 검색 요약을 해석합니다. 전체 대화 이력을 다시 전송하거나
확인 없이 조건을 자동 적용하지 않습니다. 새 후속 대화 계약은 Frontend·Core API·AI Service에 함께 반영해야 합니다.
북마크, 알림, 대화 이력의 서버 저장은 아직 구현하지 않았습니다.

검색은 `View → 페이지 ViewModel → 내부 Hook → UseCase → Repository → Fetch → Core API` 순서입니다.
채팅 Hook은 전역 `appContainer`에서 UseCase를 조회하고, 내부 Thunk가 Redux의 요청·성공·실패 상태를
변경합니다. Awilix 등록은 `app/di`에 있으며 Domain은 컨테이너를 알지 못합니다. 상세 조회는 같은
UseCase·Repository 경계를 거치되 로딩·결과 상태를 ViewModel의 로컬 state에 둡니다.

상세 조회와 원문 근거 질문은 `support-program-detail` feature 안의 별도 페이지입니다.
`SupportProgramDetailPage`는 `useSupportProgramDetailViewModel`, `SupportProgramEvidenceQuestionPage`는
`useSupportProgramEvidenceQuestionViewModel`을 대표 ViewModel로 사용하며 View·스타일·테스트를 함께 둡니다.
두 페이지는 URL의 `sourceCode`·`sourceProgramId`로 연결합니다. 채팅 feature와도 `/support-programs/detail`의 식별자로
연결하며 서로의 View·ViewModel을 import하지 않습니다. 두 기능이 사용하는 안전한 오류 문구는
`presentation/shared/support-program`에 둡니다. Domain·UseCase·Repository·DI는 기존 공용 계층을 유지합니다.

`ChatPage`는 `useChatPageViewModel`이 반환하는 상태를 렌더링하고 이벤트를 연결합니다.
ViewModel은 `chatConversationProposal`의 순수 변환으로 표시할 제안과 변경·해제·유지 조건을 계산합니다.
View는 원본 해석 상태를 재조립하지 않고 `displayProposal`을 `ConversationProposal`에 전달합니다.
검색 결과 카드는 `ProgramResults`가 렌더링하며, 카드와 결과 집계는 `supportProgramEligibility`의 분류 기준을 공유합니다.
상세 링크는 공용 `supportProgramDetailPath`를 사용합니다. 날짜·조건 문자열 서식과 화면 배치는 View에 유지합니다.
페이지 ViewModel은 `hooks/useSupportProgramChat`과 `hooks/useSupportProgramSearchReadiness`를
조합해 확인 검색·검색 재시도의 준비 상태를 검사합니다. 해석 제출·다시 해석은 준비 상태와 독립적입니다. 채팅 Hook은 Redux 상태와 해석·검색·취소·
시간 제한을 관리하고, 준비 상태 Hook은 상태 조회와 준비 중 polling을 담당합니다.
IME 조합, 스크롤 effect와 검색 결과 안내도 페이지 ViewModel이 소유합니다. 로그인 전 화면의 브랜드·화면 이동은
`presentation/shared/app-header`의 공용 헤더가 맡고, 로그인 뒤 작업 화면은 `presentation/shared/app-sidebar`의
`WorkspaceLayout`이 헤더 대신 사이드바를 놓습니다. 어떤 화면이 어느 껍데기를 쓰는지는 `App`의 라우트가 결정합니다.
두 껍데기 모두 화면 높이에 고정된 흰 바탕 안에서 안쪽 칸(div)이 스크롤하고 문서(html)는 스크롤하지 않아, 비로그인과 로그인 화면의 스크롤과 바탕색이 같습니다
(공개 화면은 `shared/app-header/PublicLayout.styles`, 작업 화면은 `shared/app-sidebar/AppSidebar.styles`). 경로(pathname)가 바뀌면 그 칸을 맨 위로 돌립니다
(`shared/routes/useResetScrollOnNavigate`). SPA는 문서를 다시 읽지 않아 브라우저가 스크롤을 되돌리지 않기 때문입니다. 쿼리만 바뀌는 탭 전환은 그대로 둡니다.
파트너 모집·기업 프로필·어드민이 함께 쓰는 카드·태그·표·버튼 스타일과 켬·끔 스위치, 지원사업 검색과 파트너 모집이 함께 쓰는
한 줄 복수 선택 필터(`FilterMultiChoices`), 연도 하나를 고르는 `YearPicker`(넓은 화면은 12년 격자, 좁은 화면은 select), 확인·입력 모달 틀
`WorkspaceModal`(포커스 가둠, Esc·배경 클릭 닫기, `tone="danger"`)은 `presentation/shared/workspace`에 둡니다.
드롭다운·말풍선·메뉴(`HelpTip`, `YearPicker`, 사이드바 계정 메뉴, 도우미 `⋯` 메뉴, 중복 검토 항목 도움말)는 같은 폴더의 `useFloatingPopover`(Floating UI)로
위치를 잡습니다. 정한 방향(기본 아래)으로만 펼치고 반대편으로 뒤집지 않으며, 좌우로 벗어나면 안쪽으로 밀고, `position: fixed`라 `overflow: hidden` 부모에도
잘리지 않습니다. 최대 높이(기본 8줄, 320px)와 펼치는 방향으로 남은 화면 안에서만 보여 주고 넘치는 내용은 안쪽 스크롤로 감춥니다. 공고 검색 결과처럼 본문에 펼치는 목록도 8건까지만 보이고 그 이상은 목록 안에서 스크롤합니다.
브라우저 기본 `<select>`는 목록을 운영체제가 그려 창 밖으로 튀어나오고 줄 수도 정할 수 없으므로 쓰지 않고, 같은 폴더의 공용 드롭다운 `SelectField`
(`role="combobox"` 버튼 + `role="listbox"` 목록, `value`·`onChange(value)`·`options` 계약, 키보드 위·아래·Home·End·Enter·Esc)를 씁니다. 출처·정렬·접수 상태·업종·소재지·
달력 연도·월·진행 단계·참여 상태·작성 문서·관리자 조건 등 모든 선택 칸이 이 컴포넌트입니다. 테스트에서는 `src/test/selectField.ts`의
`chooseOption`·`selectedValue`·`optionLabels`·`optionValues`로 값을 고르고 읽습니다(`fireEvent.change`·`.value`·`.options`는 쓰지 않음). 프로필 계정 카드의 비밀번호 변경·계정 삭제 모달은
`features/company-profile/viewmodel/useAccountSecurityViewModel`이 소유하고, 삭제에 성공하면 Store를 비운 뒤 `setTimeout(0)`으로 랜딩에 갑니다(`RequireAuth`의 로그인 리다이렉트보다 늦게). 화면 고유 배치는 각 기능의 styles 파일에서 정의합니다.
로그인 상태는 `presentation/shared/auth`의 Redux `auth` slice와 `useAuthSession`·`useRestoreAuthSession`·`useWatchAuthSession`이 소유합니다.
`App`은 시작 시 세션을 복원하고, 복원 뒤에도 `useWatchAuthSession`이 서버의 세션을 따라갑니다. 쿠키 세션으로 부르는 Core API는 `data/api/coreFetch`를 지나
401(만료·강제 로그아웃·정지로 세션 삭제)을 받으면 `signedOut('expired')`로 로그아웃시키고, 화면을 옮기거나 탭으로 돌아왔을 때 마지막 확인 뒤 5분이 지났으면 `/auth/me`로 다시 확인하며,
다른 창의 로그아웃·로그인은 세션 힌트(`govbiz.hasSession`)의 `storage` 이벤트로 따라갑니다(`signedOut('elsewhere')`·다시 복원). 로그인 화면은 끝난 이유를 한 줄로 알리고
`RequireAuth`가 남긴 `next`로 보던 화면에 돌아갑니다. 로그인·회원가입·비밀번호 확인처럼 401이 입력 오류인 요청과 Ops API는 `coreFetch`를 쓰지 않습니다. `RequireAuth(minimumTier)`·`GuestOnly`·`PublicOnly` 라우트 래퍼가 복원이 끝나기 전(`unknown`)에는
리다이렉트하지 않다가 회원·관리자 단계에 따라 화면을 나눕니다. `PublicOnly`는 로그인한 사용자를 공개 URL에서 같은 내용의
`/app` 화면으로 보내는 래퍼로, 단계는 보지 않습니다. 같은 내용을 두 세계에서 보여 줄 때 할 수 있는 일이 같으면
`layout` prop 하나로(요금제·채팅), 할 수 있는 일이 다르면 별도 feature로(파트너 모집) 만듭니다. 단계(`tier`)는 서버의 `/auth/me`가 계산해 내려 주며
로그인 화면의 `useLoginViewModel`은 `LogInUseCase → AccountRepository → accountApi` 경로로 세션을 받습니다.
새 검색 시작·현재 적용 조건 요약은
채팅 입력창 위에 간결하게 둡니다. 정상 공고 데이터 통계 패널은 표시하지 않습니다.
화면 전용 상태와 DOM ref는 Redux에 넣지 않고 Hook 로컬로 유지합니다.
상태의 자리는 "두 개 이상의 화면이 같은 데이터를 읽고 그중 한 곳이 바꾼다"면 Redux slice + thunk, 한 화면만 쓰면 Hook 로컬입니다.
서버 데이터를 Redux에 둘 때는 요청·성공·실패 단계와 어느 계정의 사본인지 함께 두고, 로그아웃·계정 변경 시 비웁니다.
View에는 JSX·스타일·ARIA 구조와 날짜·상태 문구 등의 순수 표시용 포맷을 둡니다.

| 소유자 | 현재 담당 상태 | 화면 이동·새로고침 동작 |
|---|---|---|
| React 로컬 상태 | 상세 조회, 모집글 목록·상세, 보낸 제안함, 폼 입력·확인 상자, Health, Hook SampleItem | 해당 화면이 unmount되면 초기화 |
| Redux 메모리 | 로그인 계정, 받은 제안함(사이드바 배지·제안함·모집글 상세가 공유, 수락·거절 결과 반영), 채팅 메시지·검색별 조건 스냅샷·확정 검색 의도·기업 조건·접수 상태·해석 제안·마지막 추가 질문과 미확정 초안, Redux SampleItem | 앱 내 이동 시 유지하되 비로그인 대화는 검색 흐름 이탈 시 초기화. 새로고침·로그아웃 시 초기화 |
| 서버 | MySQL 공고 카탈로그 | 브라우저 상태와 별개로 유지 |

Redux에는 직렬화 가능한 데이터만 저장하며 채팅 요청의 `AbortController`는
`useSupportProgramChat`의 `useRef`가 관리합니다.
새 대화 시작·화면 이탈 시 요청을 취소하고, `requestId`가 다른 과거 응답은 무시합니다. 새 대화
시작은 메시지·확정 검색 의도·기업 조건·접수 상태·제안·추가 질문을 초기화하며 이전 대화 목록을 보관하지 않습니다.

입력과 요청에는 다음 처리가 적용됩니다.

- 해석·검색 중 중복 제출 차단, 빈 입력 전송 차단
- 메시지의 원시 UTF-16 길이 500자 초과 시 API를 호출하지 않고 입력값을 유지하며 안내
- 한글 IME 조합 중 Enter와 Safari `keyCode 229` Enter 제출 차단
- Enter 조건 해석 전송, Shift+Enter 줄바꿈. READY라도 확인 클릭 전 검색 없음
- 검색 실패 시 내부 예외 대신 안전한 오류 문구 표시
- 검색·원문 근거 질문의 요청량 제한과 동시 처리 혼잡을 일반 장애와 구별하여 안내
- 해석이 40초를 넘으면 취소와 **다시 해석**, 검색이 90초를 넘으면 취소·검색어 복원과 **다시 검색** 제공
- 검색 서버의 유효한 `504 AI_SERVICE_TIMEOUT` Problem 응답은 별도 시간 초과 안내 제공. 알 수 없거나 잘못된 504 응답은 일반 오류로 유지하며 자동 재시도하지 않음
- 검색 재시도는 이미 확인한 command만 사용하며 해석 API를 반복 호출하지 않음
- 검색 재시도 중 새로 작성한 다른 초안은 삭제하지 않음
- 상세 조회가 10초를 넘으면 요청 취소와 오류 안내, 같은 화면의 **상세 정보 다시 불러오기**로 재조회
- 원문 질문이 70초를 넘으면 요청 취소와 시간 초과 안내, 질문 입력 보존과 수동 재전송 허용
- 원문 질문 500자 초과 시 즉시 길이 오류와 접근성 설명을 표시
- Core 상태 조회·두 SampleItem 예제 요청은 10초 상한 후 취소·오류·수동 재시도 제공
- 비동기 폼 검증 도중 수정·이탈하면 이전 입력으로 SampleItem 요청을 시작하지 않음

검색·취소 버튼은 준비 상태나 오류 안내 높이와 무관하게 검색 입력창 안에 배치합니다.

요청량 제한은 HTTP `429`와 `SUPPORT_PROGRAM_RATE_LIMITED`, 동시 처리 혼잡은 HTTP `503`과
`SUPPORT_PROGRAM_BUSY`가 일치하는 `application/problem+json` 응답에만 적용합니다. Data Layer가
계약을 검증하고 Repository가 HTTP 코드 없는 Domain `SupportProgramRequestError`로 변환합니다.
ViewModel은 서버의 `detail` 대신 고정된 한국어 문구를 표시합니다. 알 수 없거나 잘못된 `503`
응답은 기존 장애 처리로 유지합니다.

본문 `retryAfterSeconds`가 정수 `1~60`이고 읽을 수 있는 `Retry-After` 헤더와 일치할 때만
권장 대기 시간을 표시합니다. 헤더가 없거나 두 값이 잘못되면 초 단위 안내를 생략합니다.
별도 origin의 Core API는 `Retry-After`를 CORS 노출 헤더에 포함해야 합니다. 자동 재시도나
카운트다운은 없으며, 검색 대화·검색어·근거 질문을 유지한 채 사용자가 직접 재시도합니다.
화면에서 취소해도 이미 시작된 서버의 AI 실행이 즉시 중단된다는 뜻은 아닙니다.

검색 제한 90초는 Core의 순차적인 의미 검색 읽기 제한 30초와 검색 전용 점수화 읽기 제한 55초에 여유 5초를 둔 값입니다.
서버 제한시간을 변경할 때도 이 순차 호출 시간을 고려해야 하며, 90초는 응답시간 목표가 아닙니다.
상세·원문 질문도 요청 완료·화면 이탈 때 타이머를 정리하고, 취소된 요청의 늦은 응답은 무시합니다.
원문 질문 70초 역시 화면 고착 방지를 위한 상한이며 서버의 모델 실행 중단이나 비용 취소를 보장하지 않습니다.

스타일은 Tailwind `@theme` 토큰과 View 옆 `*.styles.ts`를 사용합니다. 색 토큰(`brand-primary`, `ink-muted` 등)은
`frontend/packages/shared/src/design/tokens.ts`가 원본이고, `src/design-tokens.css`는 `pnpm --filter govbiz-web tokens`로 만드는

## 중복 지원·수혜 검토 사용자 화면 (5-1)

`/app/combination-reviews`는 본인 목록·커서 조회와 검토별 최근 실행 상태, `/new`는 사업 1 · 사업 2 칸에 공고를 하나씩 골라 저장
(공고 상세의 [중복 지원·수혜 검토]는 `/new?sourceCode=…&sourceProgramId=…`로 열어 그 공고를 사업 1 칸에 골라 두고 표시 정보만 상세 조회로 채우며, 저장·분석은 보내지 않음),
`/:reviewId`는 입력 수정·실행·이력 조회를 제공하고(목록 카드는 [⋯] 메뉴 없이 오른쪽 위 휴지통 아이콘과, 실행한 검토에만 보조 링크 [입력 수정]을 둠), 실행 이력을 선택하면 `/:reviewId/runs/:runId` 결과 전용 화면에서 분석 결과·원본 다운로드를 제공한다. RequireAuth와 WorkspaceLayout을 사용한다.
호출은 `View → ViewModel → CombinationReviewUseCase → Domain Repository 계약 → Data 구현 → HTTP/Zod → Core API`다.
공고 선택은 신청 문서 새 문서와 같은 공용 `공고 고르기` 패널(`presentation/shared/support-program/ProgramPickerPanel`)이
`BrowseSavedSupportProgramsUseCase`의 관심 공고 목록과 기존 `BrowseSupportProgramsUseCase`의 무료 카탈로그 API를 재사용하며 접수 종료·미지원 자동 분석을 구분한다.

1단계는 검토 제목 카드와 "비교할 공고" 카드(`n/2`)의 사업 1 · 사업 2 칸이다. 빈 칸은 점선 카드에 [공고 고르기], 고른 칸은 신청 문서의 고른 공고 카드와 같은
접수 상태 · D-day · 출처 배지, 공고명, 기관 · 접수 기간, [공고 상세 ↗] · [바꾸기] · [빼기]를 보이고, 자동 분석을 지원하지 않는 공고는 칸 안에 알린다.
[공고 고르기] · [바꾸기]는 오른쪽 패널(600px 미만은 전체 높이 시트)을 그 칸 하나만 고르는 라디오 목록으로 연다. 관심 공고는 패널을 열 때 조회하고,
전체 검색은 접수가 끝난 공고도 보이도록 접수 상태 "전체"로 시작하며, 다른 칸에서 고른 공고는 "사업 n로 고름"으로 흐리게 두어 고를 수 없다.
[사업 n로 선택]을 누르면 그 칸에 반영하고(다른 공고로 바꾸면 그 사업의 상태는 모름에서 다시 시작), 패널을 닫거나 칸을 비우면 포커스를 그 칸의 버튼으로 돌려준다.
[빼기]는 그 칸만 비우고 다른 칸의 공고는 제자리에 둔다. 새 검토는 두 칸이 차면 제목을 "사업 1 짧은 이름 X 사업 2 짧은 이름 검토"로 채우고(지역 꼬리표·연도·"모집 공고" 같은 꼬리를 빼고 18자로 줄임, 직접 고친 제목은 덮지 않음), 저장 순서는 칸 순서이며, 제목과 두 칸이 모두 있어야 [다음 →]을 누를 수 있다. 단계 이동([다음 →]·[← 이전])마다 입력을 자동 저장하고(새 검토는 1단계 [다음 →]에서 생성, 이후 expectedRevision PUT) 스크롤을 상단으로 초기화한다. 단계는 `제목 · 공고 선택 → 공고 분석` 두 개이고(참여 상태 단계는 없앰), 현재 단계는 `?step=analysis`로 주소에 남아 새로고침·뒤로 가기·링크로 같은 단계를 연다(예전 `?step=participation` 주소는 공고 분석 단계로 연다). 유료 분석은 2단계 하단 바의 [검토 실행]에서만 접수하며, 바뀐 내 상황이 있으면 먼저 저장(expectedRevision PUT)한 뒤 그 버전으로 접수한다. 입력 충돌 시 편집 내용을 유지하고 분석은 보내지 않는다.
하단 바의 주 버튼은 신청 문서와 같이 저장 중·접수 중·분석 중을 스피너로 보이고, 누를 수 없을 때는 이유(제목 없음·공고 수·분석 중·확인 필요 실행·미지원 공고)를 버튼 앞에 적어 `aria-describedby`로 연결한다. 현재 입력으로 끝난 결과가 있으면 [결과 보기 →]가 주 동작, [다시 실행]이 보조 동작이다.
2단계 위쪽에는 대기·분석 중이면 진행 카드(서버 상태와 접수 뒤 경과 시간만 표시, 세부 단계·남은 시간은 만들지 않음), 끝났으면 최근 실행 카드([결과 보기]·[자세히 보기], 지난 입력 버전이면 안내)를 둔다.
목록 카드는 신청 문서 목록처럼 상태 배지(실행 전·분석 대기·분석 중·분석 완료·분석 실패·결과 확인 필요)·한 줄 설명·진행 줄과 상태별 버튼([이어서 입력]·[진행 보기]·[결과 보기]·[자세히 보기]·[상태 보기])을 보인다. Core 목록 응답의 `latestRun`을 쓰고, 대기·분석 중인 검토만 4초 간격으로 그 검토의 최근 실행을 다시 읽는다. 분석 중·확인 필요인 검토는 삭제를 막는다.
성공적으로 다음 단계에 들어가면 이전 단계의 검증 오류를 지우며, 내부 제공처·원본 ID는 사용자 화면에 표시하지 않는다. 공고 분석 단계의 "내 상황(선택)" 카드에서 사업별 지금 상태(모름 · 신청 전 · 신청함 · 심사 중 · 선정 · 협약 · 수행 중 · 받음 · 종료)와 두 사업의 관계 두 칸(같은 과제·제품인가요? · 같은 비용 항목에 쓰나요? — 예 · 아니오 · 모름), 실행별 추가 설명을 받는다. 모두 비워도 분석할 수 있다. 상태는 shared `CombinationReviewParticipation`의 4값 대응으로 기존 사실 6개에 저장하고(같은 상태로 읽히면 세부 사실을 그대로 둠), 관계는 검토 입력의 `relation`으로 저장한다(없던 응답은 모름).
실행 결과는 분석 화면 아래에 펼치지 않고 실행 이력 링크로 별도 결과 주소에 이동해 즉시 불러온다. 세 질문 방식(`combination-review-v3`, 사업쌍에 `answers`가 있는 실행) 결과는 결론 카드(질문별 판정 칩 · 불가 → 기관 확인 → 조건부 → 규정 없음 → 가능 순으로 코드가 정한 결론 문장 · "찾지 못함 ≠ 허용" 한 줄 · 접힌 AI 요약) → 질문 카드 3장(둘 다 신청할 수 있나요? · 둘 다 되면 함께 수행할 수 있나요? · 같은 과제·비용으로 두 번 받는 것은 아닌가요?, 판정 칩 · 설명 · "조건 → 가능/불가" 줄과 조건 근거 · 답 근거(처음부터 펼침) · 기관에 물어볼 것 · 걸리면 생기는 일(평가~사후 시점 · 조치 · 근거), 규정 없음은 허용이 아니라는 안내) → 내 상황으로 좁히기(사업별 상태 · 관계 두 칸, [저장하고 다시 분석]은 입력을 저장한 뒤 새 분석을 접수하고 그 결과 화면으로 이동) → 접힌 공식 원문 · 판단 한계 순서다. 지난 여섯 단계 방식(v2) 결과는 아래 화면 그대로 읽기 전용으로 보이고, 맨 위 안내의 [새 방식으로 다시 분석]은 저장된 입력으로 새 분석을 접수한다(분석 방식은 Core 설정이 정함). 여섯 단계 결과 화면은 결론 카드(판정 개수 · 판정 조합으로 정한 결론 문장과 이유 · 신청~교부 단계 색 띠 · "찾지 못함 ≠ 허용" 한 줄 · 접힌 AI 요약) → 먼저 확인할 것(단계마다 아직 나오지 않은 첫 질문, 주의 단계 먼저 · 질문 전체 보기 · 내 상황 입력하고 다시 보기) → 단계별 판단 줄(신청~교부 순, 주의 단계만 펼침, 근거 원문은 첫 주의 줄만 펼침, 띠를 누르면 그 줄을 펼쳐 이동) → 접힌 공식 원문 · 판단 한계 순서다. 결론 문장(v2 · v3)과 질문 고르기 규칙, 판정 색 단계는 shared `CombinationReviewResult`에 둔다. 근거 원문은 저장된 인용을 바꾸지 않고 shared `CombinationReviewEvidence`로 정리해 보여 준다(PDF 줄바꿈 잇기 · 글꼴 전용 문자와 쪽 번호 · 출력 도장 제거 · 글머리 단계 들여쓰기 · 풀린 표 칸 묶기 · 빈 서식 칸 제거). Core 근거용 추출본(문서 기록 `parserVersion`에 `-evidence-layout-`)은 줄 잇기가 끝난 상태라 다시 잇지 않고, `칸 | 칸` 표 행을 표 줄로 그리며 제한 낱말이 들면 강조한다. 기본 보기는 중복 · 제한 낱말이 든 줄과 앞뒤 한 줄이고, 위치는 "사업 1 · 파일 이름 · 3쪽"으로 쓰며, 펼치기는 인용이 원문 조각의 줄 중간에서 끊겼을 때만 "앞 내용 생략" · "뒤로 이어짐"과 [이 부분 전체 보기](조각 전체), 온전한 줄 단위 인용인데 조각에 앞뒤 줄이 더 있으면 [앞뒤 원문 보기](조각 전체, 인용한 줄을 묶어 표시), 그 밖에는 접힌 줄이 있을 때 [전체 n줄 보기]다. [원문 그대로] · "○○ 단계에도 인용" · "신청서 서식" 표시도 둔다. 실행 선택 목록으로 다른 이력으로 전환하고 이전 이력을 더 불러온다. 대기·분석 중은 자동 조회한다.
비동기 분석 접수 POST 응답을 최대 15초 기다리며 서버 작업 취소를 보장하지 않는다. 미확인 요청의 키·버전·추가 설명만
계정별 탭 sessionStorage에 보관하고, 공고 분석 단계의 [다시 시도]로 같은 요청만 재전송한다. 조회·마운트·로그인으로 POST하지 않는다.
저장소를 쓸 수 없으면 분석을 시작하지 않으며 일반 입력 초안·결과는 브라우저에 영속 저장하지 않는다.
계정 변경·로그아웃 시 기록을 지우고 이전 요청을 취소하며 세션 참조 검사로 늦은 응답을 차단한다.
QUEUED/RUNNING은 3초 간격으로 자동 조회하고 UNKNOWN은 중복 과금을 막기 위해 새 실행을 차단한다. FAILED/INTERRUPTED는 정상 근거 부족과 구분한다.

결과의 사업 순서·참여 상태·인용은 해당 Run의 스냅샷으로 표시한다. 여섯 단계의 판단 범위·질문·기관 확인·수집 한계와
자동 수집/사람 미검수 상태를 표시한다. 여섯 단계는 반응형 선택 보드에 요약하고 선택한 단계의 상세만 아래에 표시하며 원본은 세션을 포함한 GET으로 내려받는다. 5-2의 비로그인 선택 유지·작업 이어보기,
신청서 작성 도우미, 실제 OpenAI 품질 평가는 포함하지 않는다.

### 중복 검토 모의 브라우저 검증

Node 24에서 `node scripts/combination-review-mock.mjs`를 실행하고, 별도 셸에서
`VITE_CORE_API_BASE_URL=/`, `VITE_DEV_PROXY_TARGET=http://127.0.0.1:4181` 환경변수로
`pnpm dev --port 5175`를 실행한다. 모의 서버는 loopback에만 바인딩하며 외부 API를 호출하지 않는다.
`http://localhost:5175/login`에서 임의의 테스트 이메일·비밀번호로 로그인한다.
`http://127.0.0.1:4181/__scenario?mode=success`로 모드를 바꿀 수 있다.
지원 모드: success, empty, conflict, expired, 422, 429, 503, running, lost, delayed.
`/__requests`는 로컬 모의 요청 기록이며 실제 사용자 정보를 입력하지 않는다.

중복 검토 API는 최신 Core 실행 파일과 V6/V7 migration이 필요하다. Frontend만 소스 마운트로
갱신되고 Core 컨테이너가 이전 이미지면 저장 요청에 일반 404가 반환된다. 이 경우 화면은
존재하지 않는 개인 검토가 아니라 API 실행 버전·연결 주소 문제로 안내하고 입력을 유지한다.
DB 컨테이너나 볼륨을 삭제/재생성하지 않고, 승인된 Core 업데이트 시 Flyway가 스키마를 반영한다.
입력 수정 성공은 PUT 204(본문 없음)이며 자동 GET 없이 제출 입력과 다음 버전을 유지한다.
